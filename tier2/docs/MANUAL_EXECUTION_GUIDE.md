# Manual Execution Guide

This guide provides the exact commands required to manually execute the existing vulnerability reproduction harnesses and collect runtime evidence within the Android ARM64 QEMU laboratory environment.

## 1. Build Userspace Artifacts

If you have modified a C trigger in `tier2/exploit/reproducer/`, you must compile it using an ARM64 cross-compiler (e.g., `aarch64-linux-gnu-gcc` or the musl cross compiler) before injecting it into the rootfs.

**Host Command:**
```bash
aarch64-linux-gnu-gcc -O2 -static -o tier2/rootfs/trigger tier2/exploit/reproducer/trigger.c
```
- **Runs on:** Host OS
- **Expected Output:** No output if successful.
- **Success:** A statically linked ARM64 binary `tier2/rootfs/trigger` is created.
- **Failure:** Compiler errors indicating missing headers, incorrect architecture, or syntax issues.

## 2. Rebuild the Initramfs

Once the userspace artifacts (like `trigger`) are placed into `tier2/rootfs/`, you must package them into a new initramfs archive.

**Host Command:**
```bash
./tier2/scripts/build_rootfs.sh
```
- **Runs on:** Host OS
- **Expected Output:** CPIO archiving details, ending with "Ramdisk generated at: .../initramfs.cpio".
- **Success:** The file `tier2/initramfs.cpio` is updated.
- **Failure:** Script exits with an error indicating `tier2/rootfs/` is missing or permission denied.

## 3. Launch the QEMU Environment

Boot the Android ARM64 kernel using the freshly built initramfs.

**Host Command:**
```bash
./tier2/scripts/run_qemu.sh
```
- **Runs on:** Host OS
- **Expected Output:** QEMU startup log followed by Linux kernel boot messages, dropping into a `/ #` shell.
- **Success:** Interactive BusyBox root shell is presented.
- **Failure:** QEMU fails to start, kernel panics during boot, or the shell does not appear.

## 4. Execute the Existing Binary

Run the compiled test harness from within the running QEMU guest.

**Guest Command:**
```bash
/trigger
```
- **Runs on:** Inside QEMU guest
- **Expected Output:** Standard output generated by the test harness (e.g., loop iterations, timing measurements, or system call traces).
- **Success:** The binary executes without crashing the kernel, or crashes the kernel exactly as hypothesized if triggering a kernel panic.
- **Failure:** `Segmentation fault` (userspace issue), `not found` (binary not packed in rootfs), or the program silently hangs without kernel evidence.

## 5. Collect Dmesg and Runtime Output

Check the kernel ring buffer for relevant KASAN, UAF, or general fault reports.

**Guest Command:**
```bash
dmesg | grep -iE 'kasan|bug|oops|panic|epoll'
```
- **Runs on:** Inside QEMU guest
- **Expected Output:** Filtered kernel logs highlighting potential vulnerability evidence.
- **Success:** A valid kernel fault report (e.g., KASAN use-after-free) proving the vulnerability.
- **Failure:** No relevant output, meaning the vulnerability was not triggered.

Alternatively, to capture a complete timestamped evidence package of the boot sequence:
**Host Command:**
```bash
./tier2/scripts/collect_runtime_evidence.sh
```

## 6. Exit QEMU Cleanly

To stop the QEMU guest and return to the host terminal.

**Host Command (QEMU Escape Sequence):**
Press `Ctrl-a`, release both keys, then press `x`.
- **Runs on:** QEMU console (Host OS wrapper)
- **Expected Output:** `QEMU: Terminated`
- **Success:** QEMU process exits cleanly.
- **Failure:** N/A

## 7. Preserve All Logs and Evidence

If manual execution produced a kernel panic, KASAN report, or unexpected behavior, manually copy the QEMU terminal output or rely on the `collect_runtime_evidence.sh` script's generated directories in `tier2/evidence/`. Create a new entry using `tier2/docs/EXPERIMENT_LOG_TEMPLATE.md` to document the exact conditions and outcomes of the run.
